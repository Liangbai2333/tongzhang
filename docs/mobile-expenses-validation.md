日期：2026-10-25。当前分支 `feat/13-ledgers-invitation-ui`，服务端基于已同步的 `main` `574d58b`。本轮接通消费新增、列表、详情、收据、成员余额和只读结算预览，保留前一轮账本/邀请界面与真实接口。未提交、推送或修改 Issue 状态。

## 已接通范围

| 移动端入口                | 真实接口与行为                                                                                                                    |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 账本「记第一笔 / 记一笔」 | A07 读取真实成员和状态；仅 ACTIVE 允许进入表单；A13 保存消费并跳转 A15 详情                                                       |
| 消费表单                  | 金额以 `parseYuan` 转为 bigint 整数分；付款人可不参与分摊；人均、按份、按金额共用底部设置面板和 domain 分摊预览，最终由服务端重算 |
| 消费流水                  | A14 在线查询；日期、付款人、类别在服务端组合筛选；游标仅使用服务端返回值；分页失败保留已读页，整页刷新失败不展示旧流水            |
| 消费详情                  | A15 显示实际付款人、记录人、日期、分摊、备注和收据引用；未接通的编辑/删除入口保持未开放                                           |
| 收据                      | 相册选择或请求相机权限后拍摄，转 JPEG 并限制到 1 MiB；A18 上传后将真实图片 ID 放入消费提交，A19 鉴权读取已绑定图片                |

| 结算预览                  | A22 显示服务端版本、转账笔数及方案；复制完整方案，不调用正式冻结、还款或结清写接口                                                |

页面实现位于 `src/features`；新增路由只有消费新增/详情、成员余额和结算预览。类别、付款人、日期、分摊、筛选、收据预览及放弃确认均为当前页面中的面板，没有新增 Web 构建。

## 表单和失败处理

- 查询和写入均在线，业务数据不持久缓存，不建立离线队列。页面重新获得焦点时在线核验；未登录和权限错误继续走统一会话与错误处理。
- 分摊面板使用独立草稿，取消不影响表单。人均/按份用最大余数法，尾分按稳定成员 ID 分配；按金额合计必须严格等于消费金额。日期校验拒绝不存在的日期，筛选草稿只有点击应用才发送查询。
- 名称、金额、付款人、日期、分摊、备注和已选收据在失败时保留。写入期间禁用重复提交、返回和面板操作；未知消费提交锁定原输入，显式重试使用原幂等键，或返回账本在线核对。未保存输入离页需要确认。
- 上传成功后保留图片 ID，消费失败重试不重新上传。选图取消保留上一张；移除、重新选择、消费成功或离页时清理本次临时文件，不删除相册原图。服务端的临时图片定时清理仍待后续任务。
- A19 的图片字节只转为内存 data URI；`expo-image` 使用 `cachePolicy="none"`，不写业务图片文件缓存。每次打开收据重新鉴权，失败不回退到旧图片。

### SDK 57 上传兼容修复

真实原生验收发现旧上传封装的 `{ uri, name, type }` multipart 文件项被 SDK 57 默认 fetch 拒绝，报 `Unsupported FormDataPart implementation`。现改用 `expo-file-system` 的 `File`，继续复用统一 HTTP、认证、超时和错误处理。没有切换旧 fetch、添加依赖或修改原生配置。

依据：[Expo SDK 57 默认 fetch](https://docs.expo.dev/versions/v57.0.0/sdk/expo/#expofetch-api)、已安装 SDK 的 `convertFormDataAsync` 和 `File` 类型。回归测试使用已安装 SDK 的真实 multipart 编码器，验证文件内容、MIME、元数据与权限头，防止仅通过 URI 对象替身误判上传成功。

## 真实数据与原生验收

环境：iPhone 18 Pro / iOS 27.0 已安装开发客户端，Metro 8083；当前工作区 API 3313，专用 PostgreSQL 库 `tongzhang_issue13_test`。没有写入开发业务库。测试收据明确标注 TEST DATA ONLY，经系统相册选入，不作为产品内置素材。

实际链路：甲进入乙创建的两人账本 → 填写 ¥120.00 → 核对人均预览 → 系统相册选择 3000×4000 PNG → 压缩为 138919 字节 JPEG → 原生提交消费 → 详情各分摊 6000 分 → 授权读取同一收据 → 返回流水与余额 → 预览乙向甲转账 6000 分并复制。交通筛选返回真实空结果，清除后恢复记录。

核对两账号读取到同一笔消费、同一收据 SHA-256 和同一份方案；非成员查询消费列表、详情、收据均为 403。数据库只有 1 笔消费、2 条分摊、1 条收据关联、1 张绑定图片；账本版本 3、状态 ACTIVE、结算批次 0。保存离页后选图/压缩临时目录文件数为 0。结果见 [数据库与 HTTP 记录](evidence/mobile-expenses/database-checks.json)。

曾停止本任务自己的 API 检查上传失败和表单保留，恢复服务后没有自动新增消费；定位并修复上述 SDK 文件项兼容问题后原生提交成功。原有 3300 API 和其他 Metro 未调整。
