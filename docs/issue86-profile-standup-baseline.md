## 5. `profile` 模块 `A28` / `A29` 服务端实现说明

在 [repository.ts](../apps/server/src/modules/profile/repository.ts) 与 [service.ts](../apps/server/src/modules/profile/service.ts) 移除 `notReady` 的 `501` 占位，接通真实 PostgreSQL 持久化与 `operation_logs` 审计写入：

| 审查维度             | 实际实现与约束核对                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **权限与状态**       | `A04 getMe`、`A28 updateProfile`、`A29 updatePreferences` 均由 `app.authenticate` 强制校验在线有效会话，匿名、格式错误或已登出撤销的令牌统一返回 `401 UNAUTHENTICATED`；服务仅按认证上下文 `principal.userId` 操作本人记录，不接受 `userId` / `id` 跨用户修改；`users.email` 全程保持只读。个人资料与通知偏好独立于单账本 `ACTIVE / SETTLING / SETTLED` 生命周期，修改用户名后账本详情、成员列表与邀请预览通过关联查询实时展示新用户名，不篡改 `ledgers.version` 或冻结状态                                                                                                                                                                             |
| **金额与守恒**       | `A28` / `A29` 仅读写 `users.username`、`users.notification_enabled` 与 `operation_logs`，不涉及消费、分摊或结算转账表，不影响任何账本的 `bigint` 整数分总额、净额或剩余净额守恒                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **事务与幂等**       | `updateProfile` 与 `updatePreferences` 均通过 `withTransaction` 开启数据库事务，先对本人 `users` 行执行 `SELECT ... FOR UPDATE` 行锁，再更新目标列并调用 `appendAudit` 写入 `operation_logs`（`PROFILE_UPDATED` / `PREFERENCES_UPDATED`，`targetType: 'USER'`，`ledgerId: null`），用户更新与审计共享同一 `tx` 原子提交或回滚；两个 `PATCH` 接口均为绝对值覆盖语义（`A29` 直接写入布尔值 `notificationEnabled`，绝不执行 toggle 反转，重复提交相同值结果恒定）                                                                                                                                                                                          |
| **错误码与契约 DTO** | `A28` 由 `updateProfileBodySchema`（`z.strictObject`）与服务端 Unicode 码点数校验共同约束 trim 后 `2～30` 个有效字符（同时拦截 UTF-16 长度为 2 但 PostgreSQL `char_length` 为 1 的单码点生僻/表情字符及 `\0` 字节），超界、空白或携带 `email` 等多余字段一律返回 `400 VALIDATION_ERROR`；`A29` 对非布尔值或多余字段返回 `400 VALIDATION_ERROR`。响应经 `toUserSelf` 与契约 Schema 双重校验，严格输出 `{ id, username, email, notificationEnabled }` 或 `{ notificationEnabled }`，绝不泄露 `passwordHash` 等敏感列。已同步更新 [接口索引](api-reference.md)、[已知限制](known-limitations.md)、[模块说明](modules/profile.md) 与 [README](../README.md) |

## 6. `invitations` 模块 `A11` / `A12` 扫码 6 位邀请码兼容性复核

对 [issue.ts](../apps/server/src/modules/invitations/issue.ts)、[service.ts](../apps/server/src/modules/invitations/service.ts)、[invitations.ts](../packages/contracts/src/invitations.ts) 及移动端载荷解析 [qr.ts](../apps/mobile/src/features/invitations/qr.ts) 进行逐项核对，确认后端无需额外分叉接口即可完整支撑应用内相机扫码加入：

1. **载荷格式与字符集完全一致**：服务端签发邀请时生成 `qrPayload = "tongzhang:invite:v1:" + code`，`code` 固定为 6 位无歧义大写字符集 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`（排除 `0/1/I/O`，与数据库约束 `ck_invitations_code`、契约 `inviteCodeSchema` 及客户端 `parseInvitationPayload` 前缀严格一致）。
2. **7 天有效期与重置作废一致**：`INVITATION_TTL_MS = 7 * 86_400_000`（7 天）。`A10 resetInvitation` 在 `ledgers FOR UPDATE` 锁内先将旧码置 `revoked_at` 再签发新码，旧二维码解析出的 6 位码在 `A11` / `A12` 统一返回 `400 INVITE_INVALID`；超过 7 天未撤销的二维码对非成员在 `A11 previewJoin` 与 `A12 joinLedger` 均返回 `409 INVITE_EXPIRED`（已是本账本成员仍可预览/进入，不重复插入成员）。
3. **12 人上限行锁与状态保护一致**：`A11 previewJoin` 运行于 `REPEATABLE READ READ ONLY` 只读事务，满 12 人或账本非 `ACTIVE` 时返回 `200` 且 `canJoin: false`；`A12 joinLedger` 在幂等锁保护下先对所属 `ledgers` 行执行 `SELECT ... FOR UPDATE`（与消费写入、正式冻结保持同一锁顺序），持锁后**二次重读邀请状态**防止并发重置漏检，再依次校验已有成员幂等返回、7 天有效期、`ledger.status === 'ACTIVE'`（否则 `409 LEDGER_FROZEN`）及 `count(ledger_members) < 12`（满员返回 `409 MEMBER_LIMIT_REACHED` 且事务回滚不消耗幂等键）。已在 [profile.integration.test.ts](../apps/server/tests/profile.integration.test.ts) 新增从真实 `qrPayload` 解析 6 位码后的重置作废、7 天过期与第 12 席双人并发抢占实库回归。
