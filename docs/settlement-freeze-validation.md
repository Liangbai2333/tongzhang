# 正式结算与账本冻结验证

关联任务：[Issue #16 · T19](https://github.com/Liangbai2333/tongzhang/issues/16)。负责人：叶银珍（@hisoka-morow527）。

## 实现范围

接通 A23 `POST /api/v1/ledgers/:ledgerId/settlement`，复用真实余额计算和 `zero-sum-dp-v1` 精确最少笔数算法。客户端仅提交 `expectedVersion`，不接受客户端转账计划。

同一个 service 事务按以下顺序执行：

1. 获取规范化用户、路径和幂等键对应的事务 advisory lock；重放前重新校验成员与创建者权限。
2. 获取账本行的 `FOR UPDATE` 锁，再次读取权限和状态；只有创建者可以对 ACTIVE 账本提交。版本不匹配返回 `409 VERSION_CONFLICT`，冻结状态返回 `409 LEDGER_FROZEN`，无权限和不存在账本统一返回 `403 FORBIDDEN`。
3. 使用本事务读取成员、未删除消费和分摊，重算余额与最少转账计划；不另开只读事务、不使用预览缓存。余额和预览原有的 repeatable-read 只读事务保持不变。
4. 保存唯一正式批次、按稳定顺序编号的 PENDING 转账，以及成员净额字符串快照。`sourceVersion` 保存冻结前版本；金额计算始终使用 bigint 整数分，响应和 JSON 快照使用整数字符串。
5. 有转账时进入 SETTLING；零转账时直接进入 SETTLED 并设置 `settledAt`，两种情况均保存批次并增加账本版本。状态、批次、转账、审计、经过契约校验的幂等响应一起提交；任何失败全部回滚。

有效期内的相同幂等请求返回首次成功的完整响应，包括同一个批次、转账 ID 和创建时间；不会因账本已冻结而重复执行。相同键更换请求内容返回 `409 IDEMPOTENCY_CONFLICT`。重放仍检查创建者权限。不同键竞争时仅有一个请求成功。

## 实际验证

环境：Node.js 24.22.0、pnpm 12.6.0、Docker 中 PostgreSQL 17.11。新建独立数据库 `tongzhang_issue16_test`，显式设置 `TEST_DATABASE_URL`，由全局 setup 应用已提交的 Drizzle SQL 迁移；未操作开发业务库。数据库 URL 的名称须以 `_test` 结尾，连接凭据不写入本文件。

| 命令                                                        | 结果                                            |
| ----------------------------------------------------------- | ----------------------------------------------- |
| `pnpm install --frozen-lockfile`                            | 通过，锁文件未修改                              |
| `pnpm check`                                                | 共享包构建、全部类型检查、ESLint 和格式检查通过 |
| `pnpm test`                                                 | 18 个文件、112 项无数据库测试通过               |
| 显式设置 `TEST_DATABASE_URL` 后执行 `pnpm test:integration` | 9 个文件、73 项通过，其中本次新增 13 项         |

新增测试位于 `apps/server/tests/settlements.integration.test.ts`，调用生产 HTTP 路由、认证、事务、幂等与权限实现，不模拟数据库。

| 验证场景           | 实际结果                                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 预览与冻结         | 预览前后业务数据、版本和时间一致；正式提交保存真实计划后冻结；后续新增消费返回 LEDGER_FROZEN                                                                              |
| 四人验收账目       | 三笔消费总额 30000 分；净额 +3000、+6000、−3000、−6000 分；保存两笔转账 3000 和 6000 分，批次和成员净额完整                                                               |
| 零转账             | 空账本、已有消费但净额全零两种情况均保存批次并直接结清；无转账行，支持原响应重放                                                                                          |
| 权限与输入         | 匿名 401；非成员、非创建者、不存在账本 403；无效/缺失幂等键及额外客户端计划字段 400；无业务副作用                                                                         |
| 版本与重算         | 旧预览提交返回 VERSION_CONFLICT；更新版本后重算最新消费总额，排除软删除记录                                                                                               |
| 幂等竞争           | 同键并发、键与路径 UUID 大小写变化均返回同一批次；异键竞争只有一个成功；异内容同键返回 IDEMPOTENCY_CONFLICT                                                               |
| 权限重新校验       | 成功后变更创建者，旧创建者无法重放；等待账本锁期间权限变化，也无法继续冻结                                                                                                |
| 最后一步数据库失败 | 仅针对本次随机幂等键添加临时 CHECK 约束，使最终幂等 INSERT 在数据库失败；断言批次、转账、冻结状态、版本、审计和幂等记录全部回滚。finally 移除测试约束后，同键手动重试成功 |
| 结算先取得账本锁   | 真实新增消费等待后返回 409 LEDGER_FROZEN；仅原消费进入正式快照，无多余消费或分摊行                                                                                        |
| 消费先取得账本锁   | 消费提交并增加版本；等待中的旧版本结算返回 409 VERSION_CONFLICT，无批次、转账或结算幂等记录；新版本手动提交得到最新计划                                                   |

两种消费/结算竞争测试使用独立 PostgreSQL 连接持有账本行锁，通过 `pg_blocking_pids` 确认两个真实写请求已经依次排队，再释放锁；不依赖 sleep 或 Promise 启动时机猜测顺序。写请求等待期间，真实预览仍能读取已提交的 ACTIVE 快照。
