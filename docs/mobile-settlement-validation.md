# Issue #27：正式结算确认与记录

关联 [Issue #27](https://github.com/Liangbai2333/tongzhang/issues/27)。实现移动端 A23 正式冻结、A24 正式记录查询；复用已有建账、消费、余额与 A22 预览。未新增服务端接口、共享契约、依赖、原生配置或 Web 构建。

## 页面与写入约束

进入结算先在线读取账本。ACTIVE 使用原预览页；仅创建者看到“正式发起结算”。确认面板展示真实账本名称、消费总额、转账总额、笔数和预览版本，点击“返回检查”或遮罩不会发起写请求。确认发送 `{ expectedVersion }` 和本次尝试的 UUID 幂等键，提交期间禁用重复确认、返回、取消和刷新，关闭手势返回；Android 返回键也拦截提交及未知结果状态。

成功响应按 A23 的 `data.batch` 显示，随即调用 A24 查询正式批次，并同时重新查询成员名称，避免成员在预览前后变化时显示旧成员信息。SETTLING、SETTLED 的账本详情提供“正式结算记录”入口 `/ledgers/[ledgerId]/settlement`；旧预览地址也会按在线状态进入正式记录，不再重新求解预览。切换账本时重置本页内存状态，避免跨账本复用批次或提交。

记录展示批次 ID、冻结前版本、算法、创建时间、消费总额、转账方案、当前进度、收付款人、金额、登记状态、登记人/时间/备注。单笔及完整方案可复制；复制失败明确反馈。查询失败隐藏旧进度，保留显式重试；A23 已确认成功但 A24 失败时只保留已确认批次标识，不展示旧进度为当前结果。

版本冲突、冻结状态变化和权限变化会保留原面板并要求重新在线查询；查询新预览后必须重新确认。网络异常或服务端不确定结果保留原版本与原幂等键，禁止取消/普通返回，只允许显式重试或在线核对 A24。核对暂未找到批次也不清除原键；超过 24 小时不再盲目重发。没有自动重试写操作、持久化业务缓存或离线队列。

## 真实数据库与原生验证

2026-10-26 使用 Node.js 24.22.0、pnpm 12.6.0、本机 PostgreSQL 17 独立 `tongzhang_issue27_*` 数据库，应用仓库迁移；没有使用开发业务库。四个临时账号通过真实注册、登录、加入和消费 API 生成数据。使用已安装的 iPhone 18 Pro / iOS 27 开发客户端，Metro 8087 与本分支源码联调，无新增原生依赖或配置，不重建原生客户端。

1. 小安/小白各付 12000 分，小陈付 6000 分，四人三笔合计 30000 分，预览生成小丁→小白 6000 分、小陈→小安 3000 分。取消确认后真实查询仍为 ACTIVE，A24 为 `404 SETTLEMENT_NOT_FOUND`。
2. 原生确认后批次为 `f36aeb32-21c6-4ab0-942f-a4233931eee7`，账本 SETTLING；通过正式记录地址重开仍为同一批次，未再调用预览冻结。
3. 在专用权限账本以普通成员打开预览，无正式发起按钮。
4. 独立冲突账本在版本 1 面板打开后，通过真实 API 新增消费，使版本变成 2；原生确认返回 `409 VERSION_CONFLICT`，保留原摘要并提示重新预览。重新查询后摘要显示实际新增的 ¥1.00、版本 2。
5. 故障代理将请求完整送到真实 API，并在服务端已返回 201 后丢弃响应连接。原生显示结果未知、禁用返回检查；点击“在线核对正式记录”读取同一真实批次并进入 SETTLED（该账本无需转账）。没有模拟成功响应。
6. 另一个零转账账本同样丢弃首次成功响应，点击“重试原结算提交”得到已保存批次；两次 POST 的幂等键 SHA-256 摘要均为 `b4ddd924159e`，且三本测试账本各只有一个正式批次。未通过自动重试恢复。
7. 通过真实 A25 API 登记四人账本中 3000 分转账，再原生重开 A24：显示 1/2 已登记、剩余 6000 分、原登记人/时间/备注，消费总额仍为 30000 分。

故障代理仅用于本机测试，不修改项目业务代码。后半段请求的[脱敏记录](evidence/issue27/native-api-requests.json)包含方法、路径、状态、是否丢弃及幂等键摘要，不包含令牌或原始幂等键。[真实 A24 快照](evidence/issue27/real-settlement-snapshots.json)及[数据库批次数量](evidence/issue27/batch-counts.json)可核对持久化结果。
